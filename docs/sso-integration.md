# План интеграции SSO УрФУ

## Обзор

Аутентификация пользователей через единую учётную запись УрФУ.
На этапе MVP используется stub-аутентификация; переход на реальный SSO — по готовности.

## Варианты интеграции

### Вариант 1: OAuth2 / OIDC (рекомендуемый)

```
┌──────────┐    1. Redirect     ┌─────────────┐
│ Frontend │ ──────────────────► │ SSO УрФУ    │
│          │                    │ (OAuth2)    │
│          │ ◄────────────────── │             │
│          │    2. Auth code     └─────────────┘
└────┬─────┘
     │ 3. Auth code
     ▼
┌──────────┐    4. Token req    ┌─────────────┐
│ Backend  │ ──────────────────► │ SSO УрФУ    │
│          │ ◄────────────────── │ Token URL   │
│          │    5. Access token  └─────────────┘
│          │
│          │    6. Userinfo req  ┌─────────────┐
│          │ ──────────────────► │ SSO УрФУ    │
│          │ ◄────────────────── │ Userinfo    │
│          │    7. User data     └─────────────┘
└──────────┘
```

**Плюсы:** пароль пользователя не проходит через наш сервер.
**Минусы:** требуется регистрация OAuth2-клиента в IT-службе УрФУ.

### Вариант 2: LDAP bind

```
┌──────────┐   login/password   ┌──────────┐   LDAP bind    ┌──────────┐
│ Frontend │ ──────────────────► │ Backend  │ ──────────────► │ LDAP     │
│          │                     │          │ ◄────────────── │ УрФУ     │
│          │ ◄────────────────── │          │   bind result   └──────────┘
│          │    JWT token        └──────────┘
└──────────┘
```

**Плюсы:** проще в настройке, не требует регистрации клиента.
**Минусы:** пароль проходит через наш backend (требуется TLS).

## Рекомендация

**OAuth2/OIDC** — если IT-служба УрФУ предоставляет OAuth2 endpoint.
**LDAP** — как fallback, если OAuth2 недоступен.

## Данные от SSO

Ожидаемый формат данных пользователя:

```json
{
  "student_id": "12345678",
  "email": "ivanov@urfu.ru",
  "full_name": "Иванов Иван Иванович",
  "faculty": "РТФ",
  "group": "РИ-123456"
}
```

Маппинг на роли приложения:
- По умолчанию: `студент-участник`
- Капитан команды: назначается внутри приложения
- Организатор: назначается вручную админом

## Текущая аутентификация (до SSO)

Пока SSO не подключён, backend использует собственный flow:

1. **POST `/auth/verify`** — проверка `student_id` по таблице `students` (данные вуза)
2. **POST `/auth/register`** — регистрация с verification token (JWT, scope `verification`)
3. **POST `/auth/login`** — вход по `username` + пароль, выдача JWT

В `DEMO_MODE=true` при старте сидируются демо-пользователи (`backend/app/core/demo_seed.py`).
На pilot с `DEMO_MODE=false` данные загружаются через `scripts/seed_all.py`.

Переменные `SSO_ENABLED`, `SSO_PROVIDER` в `docs/.env.example` — **планируемые**; в коде пока не используются.
При интеграции SSO целевой интерфейс:

```
SSO_ENABLED=false   # текущий flow (verify/register/login)
SSO_ENABLED=true    # реальный SSO
SSO_PROVIDER=oauth2 # или ldap
```
